# 2. Концептуальное проектирование

Концептуальное проектирование определяет, из каких компонентов должна состоять система предиктивного обслуживания и как данные проходят путь от цифровой модели робота до рекомендации по ТО. В главе фиксируются цель проектирования, структура ПАК, функциональная модель, потоки данных, архитектурный вариант, технологический стек и укрупненные требования.

## 2.1. Цель и задачи проектирования

### 2.1.1. Цель системы

Цель проектируемой системы - обеспечить расчетную оценку технического состояния узлов робота-паллетизатора и прогноз остаточного ресурса на основании телеметрии паллетизационного цикла. Целевая функция системы:

`S = {D, F, HI, RUL, Aто}`,

где `D` - временные ряды телеметрии, `F` - диагностические признаки, `HI` - показатель состояния, `RUL` - остаточный ресурс, `Aто` - рекомендация для ТОиР.

### 2.1.2. Проектные задачи

На концептуальном уровне система должна: получать данные из CoppeliaSim, привязывать их к циклу и фазе движения, очищать временные ряды, рассчитывать признаки, хранить данные, строить прогноз RUL и отображать состояние оборудования. Для оценки качества прогноза далее используются показатели:

`MAE = (1/n)Σ|RUL_i - RUL^_i|`,

`RMSE = sqrt((1/n)Σ(RUL_i - RUL^_i)^2)`.

## 2.2. Общая структура системы

### 2.2.1. Компоненты ПАК

Система строится как программно-аппаратный комплекс с пятью логическими уровнями: объект моделирования, сбор данных, хранение, аналитика и визуализация. В рамках ВКР физический робот заменяется цифровой моделью, но логика обмена данными сохраняется как для будущей интеграции с реальным оборудованием.

| Python-клиент | Сбор и предобработка | Очищенные временные ряды |
| InfluxDB | Хранение данных | История измерений |

### 2.2.2. Информационная модель наблюдения

Единицей наблюдения является измерение, привязанное ко времени, циклу, фазе и приводу:

`d_k = {t_k, c_k, s_k, i, q_i, ω_i, a_i, M_i, event_k}`,

где `c_k` - номер цикла, `s_k` - фаза паллетизации, `i` - номер привода, `q_i` - угол, `ω_i` - скорость, `a_i` - ускорение, `M_i` - момент. Такая структура позволяет сравнивать однотипные фазы разных циклов.

## 2.3. Функциональная модель системы

### 2.3.1. Основные функции

Функциональная модель включает шесть функций: моделирование цикла, сбор телеметрии, предобработка, расчет признаков, прогнозирование состояния и визуализация. В IDEF0-логике входами являются параметры робота, сценарий цикла и поток измерений; механизмами - CoppeliaSim, Python-модули, БД и ML-библиотеки; управляющими воздействиями - требования к частоте сбора, составу признаков и правилам предупреждений.

[[ВСТАВКА РИСУНКА 2.3: Функциональная модель системы PdM в нотации IDEF0.]]

### 2.3.2. Расчет признаков

Для каждого окна наблюдения `W = [t0, t0 + Δt]` рассчитываются статистические и энергетические признаки:

`x_norm = (x - xmin) / (xmax - xmin)`,

`F_W = {mean(x), max(x), std(x), rms(x), slope(x), E}`,

`slope(x) = (x(t0 + Δt) - x(t0)) / Δt`.

Эти признаки далее используются в модели `HI = f(F_W)` и `RUL = g(F_W, HI)`.

## 2.4. Потоки данных и взаимодействие компонентов

### 2.4.1. Контур движения данных

Поток данных строится по цепочке: CoppeliaSim -> Remote API -> Python-клиент -> предобработка -> InfluxDB -> ML-модуль -> Grafana. Для оценки нагрузки на хранилище используется расчетный объем потока:

`V = Ns · Np · fs · b`,

где `Ns` - число контролируемых сигналов, `Np` - число приводов, `fs` - частота дискретизации, `b` - размер одного значения с учетом метаданных. Суточный объем оценивается как

`Vсут = V · Tсм · Kзм`,

где `Tсм` - длительность смены, `Kзм` - число смен в сутки.

[[ВСТАВКА ТАБЛИЦЫ 2.В: Расчет объема телеметрии для частот 1, 5, 10 Гц и разных наборов сигналов.]]

### 2.4.2. Синхронизация с фазами цикла

Для корректного сравнения циклов каждому измерению задается метка фазы: ожидание паллеты, захват, перенос, укладка, установка листа, отвод паллеты. Диагностическая интерпретация выполняется не по всему ряду сразу, а по сопоставимым фазам, поскольку момент и скорость зависят от текущей операции.

## 2.5. Анализ архитектуры системы

### 2.5.1. Сравнение архитектурных вариантов

Для ПАК рассматриваются три варианта: локальный монолит, распределенная система и гибридный вариант. Для ВКР выбран гибридный вариант: моделирование, сбор и первичная обработка выполняются локально, а хранение, аналитика и визуализация выделяются как самостоятельные компоненты. Это упрощает отладку и сохраняет возможность масштабирования.

Таблица 2.2 - Сравнение архитектурных вариантов

| Вариант | Преимущество | Ограничение |
|---|---|---|
| Монолит | Простая отладка | Трудно масштабировать и заменять компоненты |
| Распределенная система | Гибкость и масштабирование | Выше сложность интеграции |
| Гибридный вариант | Баланс простоты и расширяемости | Требует явных интерфейсов обмена |

### 2.5.2. Критерии выбора

Выбор архитектуры выполняется по критериям: воспроизводимость экспериментов, доступность данных, модульность, возможность визуального контроля, расширяемость под реальный объект. Для сравнения вариантов можно использовать интегральную оценку:

`R = Σ w_j · r_j`,

где `r_j` - балл варианта по критерию, `w_j` - вес критерия. В практической части таблица критериев будет заполнена на основе реализованного прототипа.

## 2.6. Выбор технологической реализации

### 2.6.1. Обоснование инструментов

CoppeliaSim выбран для имитации роботизированной ячейки и получения телеметрии через Remote API. Python используется как интеграционный язык для сбора данных, расчета признаков и обучения моделей. InfluxDB подходит для временных рядов, Grafana - для визуального контроля состояния, scikit-learn и XGBoost - для реализации базовых и ансамблевых моделей прогнозирования.

Таблица 2.3 - Технологический стек системы

| Задача | Инструмент | Причина выбора |
|---|---|---|
| Имитация робота | CoppeliaSim | Моделирование сцены и доступ к параметрам движения |
| Сбор данных | Python + Remote API | Гибкая интеграция и обработка |
| Хранение | InfluxDB | Временные ряды и теги |
| Визуализация | Grafana | Панели, графики, предупреждения |
| ML | scikit-learn, XGBoost | Регрессия, оценка качества, воспроизводимость |

### 2.6.2. Модель прогнозирования

На концептуальном уровне задача прогнозирования задается как регрессия:

`RUL^ = g(F, θ)`,

где `F` - признаковый вектор, `θ` - параметры модели. Для базовой проверки используется линейная или ансамблевая модель, а качество оценивается по `MAE`, `RMSE` и доле своевременных предупреждений:

`Kпред = Nсвоевр / Nпред`.

## 2.7. Формирование требований к системе

### 2.7.1. Функциональные требования

Система должна обеспечивать запуск сценария моделирования, сбор телеметрии по `motor1...motor4`, запись временных рядов, расчет признаков, оценку `HI`, прогноз `RUL`, отображение графиков и выдачу предупреждений. Минимальный набор выходных данных: таблица циклов, графики моментов и скоростей, расчетные признаки, прогноз ресурса и журнал диагностических событий.

[[ВСТАВКА СКРИНШОТА 2.7: Черновой вид будущей панели Grafana: состояние приводов, HI, RUL, события.]]

### 2.7.2. Нефункциональные и расчетные требования

Ключевые требования задаются в измеримой форме:

`Tобн <= Δtдоп`,

`Pпотерь <= Pдоп`,

`Kготовн = Tработ / (Tработ + Tпрост)`,

где `Tобн` - период обновления диагностических данных, `Pпотерь` - доля потерянных измерений, `Kготовн` - коэффициент готовности участка. Для прототипа допускается лабораторный режим, но структура данных должна позволять перенос на реальный участок.
